## 二、统一提交包结构

每人在**自己的分支**上提交以下目录（姓名用拼音，如 `deliverables/P2-sunhao/`）：

```

├── 01_报告章节.md          # 只写自己负责的章节，格式见第三节
├── 02_注释清单.csv         # 列：文件路径,新增注释行数,对应commit号
```

## 四、内容硬约束（AI 产出必须满足，违反即退回）

1. **正文形式**：Markdown；禁止粘贴 AI 对话原文、禁止"首先/其次/综上所述"式空话堆砌；每段有具体信息（做法、数据、位置、原因），不用形容词凑篇幅。
2. **数字来源唯一**：所有统计数字只能来自统一脚本输出，并在文中标注脚本名与运行日期；与 `metrics/selected_five.csv` 或第一节基线表不一致的，退回重算。
3. **结论必须可追溯**：每条判断给源码位置（`文件路径:行号`）或数据出处（csv 文件名 + 行）；暂无出处的推断显式标注"待验证"，不得写成事实。
4. **图表双件套**：流程图/结构图/CFG 必须同时交可编辑源文件与 PNG；CFG 须标注判定节点编号并给出 V(G) 计算式；图编号用"图Px-序号"，正文有引用（如"如图P3-1所示"）。
5. **AI 记录逐条登记**：05 文件每行写清工具名（如 ChatGPT/Codex/Copilot）、生成对象（具体到章节或文件）、用途、人工验证人（实名）、验证方式（如"逐行比对 Java token 不变""人工复算 V(G)=12 一致""对照源码核实每条注释描述"）。只写"已人工审核"不合格。
6. **注释红线**：只新增中文注释、不改任何业务逻辑；每人新增注释 ≥ 所负责代码行 × 25%（报告验收按 20% 口径）；注释写"做什么、为什么、边界条件"，不逐行翻译代码。
7. **协作留痕**：PR 描述参照 PR #1 格式（完成内容、源码范围、验证口径、AI 使用及复核状态）；复核人必须在 GitHub 上 Approve 留痕，口头/微信确认不算数。
